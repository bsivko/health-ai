# Производная база для запросов

База данных необязательна. Она может использоваться в records, когда объём и задачи
требуют совместных запросов по многим фактам. Оригиналы, читаемые материалы и записи
с происхождением остаются основаниями; база является воспроизводимым представлением.

## Выбор структуры

Агент выбирает схему, формат и состав источников по реальным данным и задаче
пользователя. Например, для повторяемых запросов может подойти SQLite.
В шаблоне нет готовой базы, списка обязательных источников или прикладного сборщика.
Не создавать пустые поля под отсутствующие сервисы, фиксированную раскладку чужой
книги, заранее выбранные таблицы измерений или приоритеты поставщиков данных.

## Требования к сборке

- Явно описать охват: источники, период, включённые и исключённые виды сведений.
- Сохранить устойчивые ID фактов, все представления, варианты, открытые противоречия
  и основания выбора рабочих значений. Повторы не увеличивают число событий.
- Каждое значение связано с материалом, точным локатором и оригиналом. Все входы,
  влияющие на расчёт, зарегистрированы с контрольными суммами, включая связанные файлы.
- Единицы, зоны, способы расчёта и семантику полей установить по источникам;
  не угадывать их по числам, названию приложения или положению колонки.
- Правила согласования и выбора значений определить по содержанию, без постоянного
  приоритета сервиса по имени. Неразрешённые случаи не скрывать в итоговых сводках.
- Исходные наблюдения и рассчитанные агрегаты различать. NULL не означает ноль;
  среднее по наблюдаемым дням не является средним по всему календарю.
- Не редактировать базу и исходные записи как независимые версии одного факта.

## Прикладные скрипты

Нужный сборщик и запросы агент создаёт после изучения принятых материалов. Первый
вариант проверяется в temp. Повторяемый скрипт сохраняется в scripts с описанием
входов, схемы, зависимостей, проверки и ограничений. Конфигурация ссылается только
на фактические источники внутри проекта; медицинские данные в код не зашиваются.
Проверка сборщика обязательна до использования его результатов.

## Проверка и использование

Для новой сборки использовать новый файл. Проверить целостность, связи, полноту
покрытия исходных записей, суммы входов, устранение повторного счёта и сохранность
ручных разрешений. Каждая исходная запись связана с фактом либо имеет явную причину
исключения. Частично построенную базу не использовать для ответов.

Перед запросом проверить актуальность входов и охвата. SQLite открывать в режиме
read-only. Новый источник, изменение данных, схемы или правил выбора требует
проверенной пересборки, а не предположения об автоматическом обновлении.
Вместе со средними и итогами показывать доступный охват и пропуски.

Простое соединение наблюдений по дате не устанавливает причинность. Старые результаты
в outputs остаются датированными снимками и не обновляются автоматически.
